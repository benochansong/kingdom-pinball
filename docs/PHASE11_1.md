# PHASE 11.1 — 핀볼 물리·도랑 밸런스

2026-11-27 · 0.11.1-beta.1 · 기준 커밋 `b0c9be4`.

실제 소스에 물리 보호 포스트, 발사 보정, BALL SAVE, 킥백, HUD와 진단을 반영했다. [전체 측정표](PINBALL_MEASUREMENTS.md)는 수정 전후 각 4,800회의 실제 Matter.js 시뮬레이션과 별도 경제 실행 240회를 담는다. 사람의 조작감 검증과 장기 경제 균형은 아래 제한사항을 함께 읽어야 한다.

## 1. 원인 분석

기존 하단 가이드 바깥으로 진입한 공은 플리퍼 접점 밖의 도랑을 따라 내려가며 복귀 충돌면이 부족했다. 기본 입력의 오른쪽 손실 직전 접촉은 주로 오른쪽 하단 외벽 부근 `(508~513, 756~763)`에 몰렸다. 발사 통로와 도랑 사이의 벽은 존재했고, 손실 판정은 실제 하단 `y > 884`였다. 조기 손실 판정이나 우측 플리퍼의 별도 강화/약화가 원인은 아니었다.

25% 발사는 기존 속도로 상단을 통과하지 못해 basic 표본 300/300회가 발사대로 회수됐다. 오른쪽 슬링 그래픽을 왼쪽과 대칭으로 그린 부분, 게이트 그래픽의 위치/각도는 실제 충돌체와 달랐다.

**자동 입력 전체에서 우측 우세가 항상 재현되지는 않았다.** 기준 basic 손실은 왼쪽 332, 오른쪽 265회였고 timed에서는 왼쪽 109, 오른쪽 118회였다. 따라서 사용자의 특정 조작/배치에서 나타난 우측 편중을 모든 상황의 성질이라고 단정하지 않는다. 양쪽 실제 손실과 조기 아웃을 줄이는 방향으로 수정했다. 슬링이 우측 손실의 단독 원인이라는 인과관계는 미측정이다.

## 2. 변경한 구조

표준 테이블 하단에 `(110,781)`, `(466,781)`, 반지름 18px의 실제 충돌 포스트를 추가했다. 접근 법선 속도 70px/s 초과 시 공별 500ms 간격으로 접촉 법선 방향 최소 500px/s 반발을 적용한다. Matter 충돌 해결 뒤 반발을 적용해 엔진이 충격량을 상쇄하지 않도록 했다. 접선 속도는 유지하며 전체 속도 상한 1,380px/s를 따른다.

포스트는 점수·생산·콤보·마법·킥백 충전에 기여하지 않는다. 외벽을 닫거나 공을 중앙에 순간이동시키지 않는다. 금색 포스트와 기존 충돌 입자, 별도 보호 효과를 표시한다.

## 3. 도랑 입구와 반사 각도

기존 가이드는 왼쪽 `(86,675)→(177,790)`, 오른쪽 `(492,675)→(399,790)`를 유지했다. 기존 저장 건물 및 지역 구조와의 충돌 위험 때문에 레일 각도를 일괄 변경하지 않았다. 포스트의 원형 접점에 따라 반사 방향이 달라진다. 바깥/안쪽 통과 틈은 약 24/30px 이상으로 지름 20px 공의 실제 아웃 경로를 남겼다. 경계 각도·속도 조합의 테스트에서 복귀와 정상 아웃 모두 확인했다.

레일은 실제 직사각 충돌체의 두께와 끝단 연장 4px를 그림에도 반영했다. 슬링의 상단·중앙 반발 값은 유지하고 표준 테이블의 연속 충격에 180ms 간격을 적용했다. 포스트 반지름·위치는 난이도별로 바뀌지 않는 안전한 공통 프리셋이다.

## 4. 발사 경로

발사 최소 속도를 880→1,060px/s로 올렸다. 60%에서 1,102px/s, 100%에서 기존 1,250px/s에 이어지는 곡선을 사용한다. 60% 이상 강한 발사는 기존 곡선을 유지한다. 게이트를 닫을 때 겹치는 공이 없는지 확인한다. 회수된 약한 공에 새 보호 예산을 지급하지 않는다. basic 25% 표본의 회수 종료는 300→18회로 감소했다. 회수 18회는 실패를 숨기지 않고 별도로 기록한다.

## 5. 플리퍼 제어

피벗 `(181,786)/(395,786)`, 길이 100, 상승/하강 속도 17/7, 반발 계수 0.62와 실제 캡슐 접점 충격 계산을 유지했다. 뿌리·중간·끝 접점, 대응 좌우 속도, 입력 시점별 물리 반응을 자동 검사했다. 자동 조준은 추가하지 않았다. 구조 보정 후 basic의 공당 실제 상승 타격은 5.77→9.67회였다. 크래들·패스·소프트 캐치의 사람 체감 평가는 미측정이다.

## 6. BALL SAVE

메인 영역에 진입해 게이트가 닫힐 때 한 번만 보호 타이머가 시작된다. 마지막 실제 공이 드레인을 통과하고 시간·횟수가 남아 있으면 라이프/코어 에너지를 소모하지 않고 발사대에 준비한다. 자동 발사하지 않는다. 무료 공에서도 원래 만료 시각과 남은 예산을 유지하며, 다음 유료/기본 공에서만 갱신한다. 일시정지 시간은 제외한다.

소비 예산을 공 생성 전에 저장한다. 저장 복원으로 첫 공 보호를 반복 지급하지 않는다. 멀티볼 임시 공 손실은 무료 보호를 사용하지 않으며 마지막 공에만 적용한다. TILT·연습·고유 도전 규칙에는 추가 보호를 적용하지 않는다.

## 7. 킥백

각 측면에 최대 한 번의 충전을 저장한다. 1초 이상 떨어진 서로 다른 유효 목표물 타격을 5/8/12회 누적해 해당 측면을 충전한다. 포스트·벽 접촉은 충전하지 않는다. 도랑 작동 구역을 아래로 통과하는 동일 공에 위쪽 충격을 주고 충전을 소비한다. 공을 추가 생성하지 않으며 재발동 간격은 2초다. 이는 항상 충돌하는 물리 포스트와 별개의 유한 보호 기능이다.

## 8. 난이도

| 설정 | BEGINNER | NORMAL | EXPERT |
|---|---:|---:|---:|
| 일반 공 보호 | 12초 | 8초 | 3초 |
| 첫 공 보호 | 15초 | 10초 | 3초 |
| 무료 복구 | 2회 | 1회 | 1회 |
| 한쪽 킥백 충전 | 5타 | 8타 | 12타 |

전쟁 난이도와 독립적이며 새 게임부터 반영한다. 기존 저장의 물리 안전을 위해 구조 차이는 적용하지 않았다. 서버가 온라인 양쪽에 NORMAL을 강제한다. 퍼즐·사용자 제작 테이블은 기존 authored 물리 및 고유 규칙, 단일 코어는 기존 손실 규칙을 유지한다.

## 9. 왼쪽·오른쪽 아웃 비교

아래는 보호 없이 3개 기본 테이블 × 4강도 × 100시드 = basic 1,200회씩이다. 발사당 비율이며 회수와 90초 상한 종료를 포함한 분모다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| 왼쪽 아웃 / 전체 발사 | 27.67% (332) | 20.17% (242) |
| 오른쪽 아웃 / 전체 발사 | 22.08% (265) | 11.75% (141) |
| 양쪽 도랑 / 전체 발사 | 49.75% (597) | 31.92% (383) |
| 오른쪽 / 양쪽 도랑 아웃 | 44.39% | 36.81% |
| 중앙 아웃 | 0 | 0 |
| 발사대 회수 종료 | 383 | 52 |
| 90초 상한 도달 | 220 | 765 |

이 봇의 중앙 손실이 0인 것은 중앙 드레인이 막혔다는 뜻이 아니다. 별도 중앙 낙하 테스트는 정상 아웃을 확인한다. 정상 입력 실패 패턴 전체를 대표하는 봇은 아니다. 수정 후 남은 손실은 오히려 왼쪽 비중이 높아 완전한 좌우 균형 달성을 주장하지 않는다. 25% 발사 실패의 영향을 뺀 50–100% 900회에서도 양쪽 도랑은 66.33%→31.00%, 오른쪽은 29.44%→11.56%였다.

## 10. 조기 아웃

같은 basic 1,200회 분모: 3초 이내 0→0, 5초 이내 6→0(0.50%→0%), 10초 이내 110→5(9.17%→0.42%), 15초 이내 250→29(20.83%→2.42%). 첫 접근/유효 타격 이전 손실은 각각 76→44(6.33%→3.67%)다.

도랑 안에서 플리퍼 아래 중앙으로 이동한 공을 중앙 아웃/접근 성공으로 잘못 세던 초기 분류를 발견해 수정했다. 실제 가이드 바깥 진입과 유효 접근 영역을 사용해 기준·최종 값을 전부 다시 측정했다. [기준 대조](pinball-baseline-verification.json)에서 원래 기준 4,800회의 물리 시간·타격 결과와 재실행이 모두 일치했다.

## 11. 공 관찰 시간

basic 평균 관찰 길이는 29.62→73.21초, 중앙값 14.57→90초, 관찰 최대 90→90초다. 이는 **발사부터 드레인/회수/90초 상한 중 먼저 발생한 시점까지**이며 완결된 평균 생존 시간이 아니다. 수정 후 63.75%가 90초 상한에 도달했다. 50–100%만 보면 평균 37.71→74.16초다. 사람의 초보 25–40/일반 40–65/숙련 70–120초 목표는 미측정이다.

실제 게임 진단은 물리 공 기록과 무료 복구를 포함한 원정 시간을 별도로 저장한다. 경제 측정의 원정 시간은 재발사 대기를 포함하며 상세 값은 별도 원본에 있다.

## 12. 조작 기회

basic 공당 유효 플리퍼 타격 5.77→9.67, 접근 5.84→9.81, 범퍼 타격 14.44→24.09회다. 50–100%만의 유효 타격도 7.70→9.77회로 늘었다. 접근한 공의 첫 접근 평균은 6.70→7.84초로 늦어졌다. timed는 0.94→1.40타에 그쳤으므로 이 입력을 실제 숙련자로 해석하지 않는다. 무입력은 0타이며 긴 자동 바운스 자체를 좋은 조작감으로 간주하지 않는다.

## 13. 재발사 회귀

왼쪽/오른쪽/중앙 손실, 보호 소진, 저장 복원, 일시정지, 에너지 부족·회복, 마지막 공, 일반 공 재생성, 멀티볼/CORE STORM, 몸체 소실 복구와 양쪽 온라인 좌석 검사를 통과했다. 무료 공의 에너지 유지와 다음 정상 손실의 단 한 번 20 에너지 지불을 검사했다.

실제 개발 브라우저에서도 25% 물리 발사 → 메인 진입 → 드레인 → 무료 준비 → 저장 복원(예산 유지) → 다음 정상 손실(100→80 에너지, 손실 1)을 확인했다. DEV 버튼은 실제 GameStateManager를 고정 시간 진행시키며 정상 프레임률 측정은 아니다.

## 14. 경제·전쟁 영향

별도 실제 GameStateManager 240회(왕국/전쟁 × 3난이도 × 보호 켬/끔 × 4강도 × 5시드)를 실행했다. 최종 물리 구조에서 보호 유무를 비교한 것이며 구버전 경제와의 완전한 전후 비교는 아니다. NORMAL 왕국의 평균 생산은 목재 79.75→80.35, 석재 34.85→36.25, 금화 70.25→71.40, 식량 117.55→118.45, 마력석 16.65→17.30이었다. 전쟁 코호트에서는 생산량 차이가 없었다. 원본에 마법·멀티볼·궁극기 충전도 기록했다.

전쟁 준비가 180초이고 측정 상한은 90초라 실제 전투 AI의 승률/병력 효율은 미측정이다. 스킬·멀티볼을 자동 발동하지 않는다. 기존 생성·보상 상한과 생산 대기시간을 유지했으며 모든 자원을 일괄 감소시키지 않았다. 장기 경제 및 궁극기 연쇄 효율은 추가 사람 플레이 평가가 필요하다.

## 16. 실제 테스트

전체 Vitest **21개 파일, 286개 테스트 통과**, 선택적 장시간/생성 테스트 2개는 건너뜀. 새 전용 검사는 30개다. 8개 지역 장치/포털 출구와 보호 포스트 간격, 10개 특수 공, 3/5/7/10공 수명주기, 플리퍼 대응 접점, 실제 생산, 온라인 양쪽 비용, 고유 퍼즐 회귀를 포함한다. 최초 제한 환경에서 두 WebSocket 검사가 `EACCES`로 실패했고 로컬 연결이 가능한 환경에서 전체 재검사해 통과했다.

수정 전/후 9,600회와 실제 경제 240회를 완료했다. 입력 정책은 none/basic/timed/mirrored이며 모든 테이블·강도·정책 조합에 100시드를 사용했다. mirrored는 트리거 오차 부호 반전이며 테이블 전체 반전이 아니다.

브라우저에서 최종 버전, 금색 실제 포스트, 보호 HUD, 설정·준비 화면과 콘솔 오류 없음 확인. 390/768/1366px 요청 뷰포트에서 가로 넘침 없음, HUD가 테이블 위 독립 영역에 배치됨을 확인했다. 브라우저 스크롤바로 실제 문서 너비는 각각 375/753/1351px였다.

`npm run build`(TypeScript 포함), `npm run server:build` 모두 성공. 최종 클라이언트 게임 JS 595.97kB(gzip 205.50kB), Matter 84.30kB, Phaser 1,208.18kB, CSS 60.83kB. 서버 번들 399.3kB. 로컬 프로덕션 미리보기에서 확인했으며 공개 배포는 수행하지 않았다.

## 18. 제한사항

내장 브라우저에서 화면 갱신과 게임 시간이 실제 벽시계보다 느리게 진행되는 현상이 남아 있다. DEV 고정 진행으로 생명주기를 검증했지만 이번 작업으로 안정적인 60FPS나 실제 기기 입력 지연 개선을 입증하지 않았다. 기존 대규모 군대+10공 렌더 성능 제한도 그대로다.

90초 검열이 많고 무입력에서도 오래 유지되는 공이 있으므로 더 긴 랠리가 모두 능동적인 플레이인 것은 아니다. 사람의 패스·캐치·전략과 장시간 전쟁/경제 검증이 남아 있다. 자동 결과에서 중앙 손실이 없고 좌우 손실도 동일하지 않으므로 모든 테이블/건물 배치의 공정성을 보장하지 않는다.

진단은 현재 모드·난이도 세션 기준이며 최근 물리 기록 2,000개, 원정 시간 1,000개, 궤적 240점, 충돌 32개로 제한한다. 통계는 장기 계정 누적 데이터베이스가 아니다. 충돌 표시 좌표는 충돌 시 공 중심이고 접촉 표면의 정확한 점은 아니다. 사람의 원래 우측 편중 상황과 장기 밸런스 목표는 추가 확인 대상이다.

## 19. 직접 플레이 확인

1. 일반 Chrome/Edge에서 클래식의 25/50/75/100% 발사와 A/D 플리퍼를 사용해 양쪽을 실제로 받아쳐 본다.
2. 뿌리/끝 접점, 늦고 빠른 입력, 길게 유지한 캐치·패스가 자연스러운지 확인한다.
3. 새 게임별 세 난이도에서 보호 HUD, 무료 공 직접 발사, 예산 소진 뒤 정상 비용을 확인한다.
4. 양쪽 목표물로 킥백을 충전한 뒤 실제 도랑 진입, 한 번 소모, 재충전을 확인한다.
5. 실제 사용하던 건물·지역·특수 공·10공 상태에서 끼임과 과도한 자동 바운스 여부를 확인한다.
6. 장기 왕국/전쟁에서 생산·병력·마법 빈도가 지나치게 쉬워졌는지 확인한다.

## 재현 명령

PowerShell, 프로젝트 루트에서 실행한다. 각 측정은 실제 엔진이므로 수 분 이상 걸릴 수 있다. `BALANCE_BASELINE`은 구버전 물리를 보존한 authored 프리셋을 선택하며 분류 코드는 양쪽에서 같다.

```powershell
$env:BALANCE_TRIALS = '100'
foreach ($tableName in @('classic','kingdom','war')) {
  $env:BALANCE_TABLES = $tableName
  $env:BALANCE_BASELINE = '1'
  npx tsx scripts/pinball-balance.ts "baseline-$tableName"
  Remove-Item Env:BALANCE_BASELINE
  npx tsx scripts/pinball-balance.ts "final-$tableName"
}
Remove-Item Env:BALANCE_TABLES
node scripts/pinball-merge.mjs before
node scripts/pinball-merge.mjs after
$env:BALANCE_TRIALS = '5'
npx tsx scripts/pinball-protection.ts
Remove-Item Env:BALANCE_TRIALS
node scripts/pinball-report.mjs
npm test
npm run build
npm run server:build
```

원본 결과는 `pinball-before.json`, `pinball-after.json`, `pinball-protection.json`, 집계는 `pinball-comparison.json`이다. 소규모 후보의 집계는 `pinball-tuning.json`에 분류 방식과 함께 보존한다. 초기 부정확한 분류 결과는 최종 성과 수치로 사용하지 않는다.
