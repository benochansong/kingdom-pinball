# ROYAL RESCUE CANNON — 실제 도랑 설치 및 포착 실패 수정

2026-11-27 · **0.11.2-beta.2**

검증 흐름: 실제 도랑 진입 → 같은 물리 공 포착 → 대포 내부 고정 및 사용량 저장 → 중앙 발사 → 플리퍼로 정상 플레이. 장식이나 HUD 변경만으로 처리하지 않았다.

## 1. 포착하지 못했던 실제 원인

- 기존 방향 필터가 **중앙 방향 수평 속도**를 가진 공을 구조 대상에서 제외했다. 실제 궤적에서 왼쪽 외벽 반사 후 vx 약 +280px/s, 오른쪽 반사 후 약 -441px/s인 공이 여전히 도랑에 있는데도 지나쳐 손실됐다. 도랑 다각형 자체로 위치를 구분하고 이 잘못된 방향 제외를 제거했다.
- 도랑 하부의 위치 판정만 사용해 상단 진입을 늦게 감지했고, 이전 위치에서 현재 위치까지의 통과 검사도 없었다. 도랑 상단부터 이어지는 센서와 이동 구간 검사를 추가했다.
- 기존 발사는 중앙 쪽 별도 출구로 공을 옮겼다. 실제 도랑에서 발사하도록 출구와 고정 위치를 일치시키고 내부 가이드에 개폐 통로를 설치했다.
- 고정 상태에서 선속도·각속도를 명시적으로 매번 0으로 갱신하도록 강화했다. 기존에도 static 전환은 있었으므로, 모든 실패를 단순히 속도 초기화 누락 때문이라고 판단하지 않았다.

## 2. Capture zone

600×900 논리 테이블 기준이다. 왼쪽 센서는 `(58,708) → (104,708) → (163,784) → (163,840) → (112,840) → (58,758)`의 볼록 다각형이며, 오른쪽은 `x → 576-x`로 대칭 배치했다. 실제 Matter sensor body와 공 반지름을 포함한 충돌을 검사한다. 경계 상자 전체를 사각 센서로 쓰지 않는다.

이 영역은 외벽과 내부 경사 가이드 사이를 따라가며, 중앙 플레이와 x554의 발사 통로를 제외한다. 공이 센서를 한 스텝에 통과해도 이전 위치→현재 위치를 공 지름 두께로 검사한다. 최소 하강 속도는 5px/s이고, 상승 공은 제외한다.

## 3. 구조와 손실 판정 우선순위

코드를 조사한 결과 **기존에도 구조 업데이트가 물리 스텝 전후에 배치되어 있었다. 순서가 거꾸로였던 것이 주원인은 아니다.** 이 순서를 유지하며 물리 스텝 후 통과 감지를 보강했다. 포착 성공 시 즉시 `heldBalls`에 등록하고 controlled 상태로 전환한다. held 공은 일반 충돌·특수 공 회복/손실·전투 궤적·끼임 복구·최종 drain에서 제외된다.

포착할 수 없거나 횟수가 없으면 기존 손실 처리가 실행된다. 이미 손실된 공을 복제해서 구하지 않는다. 온라인 권위 시뮬레이션도 동일한 컨트롤러를 사용한다.

## 4. Anchor, hold, 실제 발사

- 왼쪽 **(110,820)** / 오른쪽 **(466,820)**: 플리퍼 바깥쪽 실제 도랑의 포착 받침 내부.
- 감지 즉시 같은 body를 static/sensor, collision mask 0으로 전환하고 선속도·각속도·힘·토크를 0으로 만든다.
- 100ms 동안 도랑 안에서 anchor로 이동하고 **300ms 고정**한다. 고정 중 매 업데이트마다 위치와 속도를 유지한다.
- 원래 질량·마찰·충돌 설정을 복원하고 좌우 각각 ±45° 위 방향, **1,175px/s**를 부여한다. 발사 시 중앙으로 `setPosition`하지 않는다.
- 내부 경사 가이드 하부를 실제 물리 셔터로 분리했다. 발사한 쪽만 350ms 열리고, 다른 공과 겹치면 닫기를 연기한다. 발사 경로 170px를 중력 궤적과 장애물에 대조한다.
- 중앙 x165~411, y<675 재진입 및 발사 후 700ms 경과를 모두 만족해야 다음 구조가 가능하다.

금속 포신·열린 포구·포착 받침·왕실 장식·충전 발광·발사 효과가 물리 장치 위치와 일치한다. 기존 긴 화살표 표현을 제거했다. `CAPTURED`와 `RESCUE SHOT!` 메시지를 표시하고 두 발 소진 시 양쪽 모두 어두운 EMPTY 상태가 된다.

## 5. 왼쪽 대포 결과

실제 브라우저 DEV 격리 세션에서 x75,y680, 초기 하강 60px/s로 진입시켰다. 공 ID 67이 약 (64.50,698.68)에서 포착되고 (110,820)에서 속도/회전 0, 1/2로 고정된 뒤 중앙으로 이동했다. 손실 0, BALL SAVE 0, 코어 에너지 100을 유지했다.

별도 클래식 세션에서는 구조된 **공 ID 455를 키보드 A/D로 2회 실제 타격**했다. 자동 플리퍼가 아닌 브라우저 입력 결과다. 같은 공이 유지됐고 추가 구조는 사용하지 않았다.

## 6. 오른쪽 대포 결과

같은 왕국 세션에서 x501,y680, 초기 하강 60px/s로 진입시켰다. **동일한 공 ID 67**이 약 (513.50,698.73)에서 포착되고 (466,820)에서 고정됐다. 0/2로 차감된 뒤 (214.03,601.73)까지 중앙 좌상향으로 복귀했다. 오른쪽 벽/발사 통로로 돌아가지 않았다.

고속 좌우 구조를 마친 클래식 공 ID 269도 브라우저 A/D 입력으로 **실제 플리퍼 타격 1회**를 기록했다. 두 셔터는 이후 닫힌 상태였다. 이 세션의 구조 중 공 손실은 없었다.

## 7. 빠른 공 낙하 결과

- 자동 회귀: 좌우 각각 초기 하강 **6 / 60 / 900 / 1,320px/s**, 즉시 정지·고정·차감·같은 공 발사·중앙 진입 통과.
- 이동 구간 검사: 이전 y680에서 현재 y890으로 센서와 drain을 건너뛴 표본도 drain 전에 포착됨을 양쪽에서 검사했다. 이 큰 점프는 누락 방어용 합성 표본이며 정상 240Hz 물리의 이동량을 의미하지 않는다.
- 실제 브라우저: 좌우 초기 1,320px/s, 공 ID 269의 포착 시 기록 약 1,328px/s. 양쪽 anchor에서 선속도·회전 0을 확인하고 중앙 복귀했다.
- [240회 경로 실험 원자료](OUTLANE_RESCUE_MEASUREMENTS.json): 클래식·왕국·전쟁 × 좌우 × 구조 켬/끔 × 20개 진입 조건. 구조 켬 **120/120 중앙 복귀**, 발사 0.3초 이내 아웃 0, 같은 body 유지, body 증가 0, 비정상 수치 0. 자동 반응형 플리퍼 타격은 109/120이다.

실험 재현: `npx tsx scripts/outlane-rescue-balance.ts`. 구조 끔 120회는 약 0.55~0.57초 평균으로 도랑 손실에 도달했다. 구조 켬 관측은 모두 30초 상한에 도달했으므로 이를 실제 평균 생존 시간으로 해석하면 안 된다. 기본 목표물과 단순 반응형 플리퍼를 사용하는 물리 경로 실험이며 BALL SAVE·경제·전투·끼임 복구는 실행하지 않는다.

## 8. 성공 시 횟수 차감 및 실패 처리

감지만으로 차감하지 않는다. anchor 도착과 hold 진입에 성공할 때 `used += 1`과 `pending.charged = true`를 함께 저장한다. 발사에서는 다시 차감하지 않는다. 마지막 구조의 충전 중 0/2 저장도 복원할 수 있고 중복 차감하지 않는다.

사전 경로 검사 실패는 0회 소비한다. 고정 후 경로 차단·비활성화·공 제거는 예약한 1회를 정확히 한 번 반환한다. 취소 시 기존 공을 해제하고 기존 손실 규칙으로 돌아간다. 좌우가 같은 총량 2회를 공유하며 재발사·일시정지·저장 복원·내부 모드 전환으로 충전되지 않는다. 명시적인 새 게임만 새 총량을 받는다. 샌드박스의 기존 0~10회 설정은 유지한다.

## 9. BALL SAVE, 재발사, 회귀 검사

브라우저의 좌우 구조 성공에서 BALL SAVE 0회·손실 0회를 확인했다. 소진 후 세 번째 고속 도랑 진입은 포착하지 않고 기존 손실 1회로 넘어갔다. 일반 손실의 에너지 결제는 기존 재발사 대기 후에 실행된다.

자동 회귀에서는 다음을 검사했다.

- BALL SAVE가 있는 실제 drain은 무료 준비 공으로 전환; 보호 없는 손실은 1회 손실, 에너지 20 차감, 재발사 준비.
- 고정 중 공 제거, 사전/발사 직전 경로 차단, 소진 도랑의 받침 통과, 고정 중 충돌/보상 억제.
- 3/5/7/10개 멀티볼의 주 공 한 개만 포착, 승계 공, 특수 공 10종, CORE STORM과 기존 마법 회귀.
- 왕국·클래식·전쟁의 충전 중 복원, 마지막 구조 사용량 유지, 캠페인 8지역, 도전 모드/샌드박스/퍼즐 경계.
- 온라인 각 좌석의 독립된 두 발 및 스냅샷, 실제 WebSocket 연결·재연결·지연 회귀.

검증 합계 **354개 통과, 기존 선택적 검사 2개 건너뜀**(구조 전용 68개). 로컬 전체 실행에서는 샌드박스의 localhost `EACCES`로 온라인 두 항목이 실패했으며, 접속 허용 환경에서 관련 3개 테스트를 재실행해 모두 통과했다. 클라이언트·서버 빌드 통과. 브라우저 검사 중 콘솔 오류 0건.

## 11. 남은 문제 및 제한

- 검사한 기본 테이블/캠페인 경로에서 포착 누락·복제·중복 차감은 재현되지 않았다. 임의의 사용자 건물/공이 발사 경로를 막으면 구조를 취소하고 횟수를 반환한다. 모든 배치에서 무조건 발사를 보장하지 않는다.
- 임시 멀티볼 전체를 동시에 구하지 않는다. 주 공 하나를 우선하며 마지막 승계 공은 기존 설정을 따른다. 퍼즐·커스텀 테이블은 자체 규칙을 유지한다.
- 물리 경로 실험은 사람 실력별 성공률·평균 생존 시간·장시간 전쟁 균형의 증거가 아니다. 온라인 검증은 권위 시뮬레이션 및 로컬 WebSocket 자동 검사이며, 이번 핫픽스에서 두 사람의 원격 브라우저 대전을 수행한 것은 아니다.
- 이 작업은 로컬 실행 및 저장소 수정이다. 공개 프로덕션 배포는 수행하지 않았다. 기존 11.2 문서와 RESCUE_MEASUREMENTS.json은 이전 구현 기록이며 현재 결과는 이 문서와 OUTLANE_RESCUE_MEASUREMENTS.json을 기준으로 한다.
